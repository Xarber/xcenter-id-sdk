# Integrate X-Center ID

## Run the integration

Treat requests to use X-Center ID for sync or permissions as implementation requests. Work in the target app repository, trace its existing account and storage paths, and use the [integration contract](references/integration.md) and [capabilities](references/capabilities.md) to implement the requested changes. Preserve current data and account recovery. The production issuer is https://id.xcenter.it. Use the [public X-Center ID SDK](https://github.com/Xarber/xcenter-id-sdk) as the maintained source for reusable components.

1. **Check registration early.** Inspect existing configuration for the target product. Find its exact registration and status in the [Developer Portal](https://id.xcenter.it/developer) when signed-in access is available. A client ID in source is insufficient evidence. If missing, establish the app name, client type and exact owned HTTPS callback from its source or infrastructure. Use the portal to register or reuse the matching app and publish its supplied TXT challenge when the user has authorized those actions and access is available. Verify public DNS and use **Verify domain and activate**. If any step needs the user, ask promptly for the single concrete action, including the exact callback and live TXT challenge when known. Never invent a challenge or ask for secrets in chat.
   **Strongly recommend uploading the real product icon during portal registration.** Locate an existing app icon early, prefer its square export, and upload it with **Choose app icon** when portal access is available. Confirm the preview and the consent screen identify the right product. If no approved asset is available, ask for one while continuing integration. The fallback icon still works and an icon is optional for activation and testing.
2. **Configure permissions in the registration.** When the portal offers the visual sharing editor, select a published source collection and write its consent title, or open **App configuration** to copy and update the selected registration’s versioned JSON. On an older portal, use its database sharing settings. See [app configuration](references/capabilities.md#app-configuration). Keep callback verification and user consent as explicit steps.
3. **Keep coding while activation is pending.** Implement the host app's normal sign-in or account link, secure product session, and requested sync and permission flows. Keep credentials in deployment configuration. Use a controlled test environment and leave production features gated until activation and the relevant access checks succeed.
4. **Finish setup and verify.** For private user storage, confirm active registration and request `app_data` through user consent. For app-owned service storage and publishing shared collections, also confirm administrator **Verify app**. Verify sync through the normal product flow. Report portal/DNS state, code changed, verified flows and any exact external action still needed. Instructions alone are an appropriate result only when the user asked for guidance or the repository is inaccessible.

**Require iOS `ASWebAuthenticationSession`** for sign-in. The sheet closes automatically when the verified HTTPS callback is received or after a validated backend handoff. Use a system Custom Tab with an Android App Link on Android and a top-level HTTPS backend redirect on the web. Use Authorization Code with PKCE. Offer [QR or manual device-code sign-in](references/integration.md#qr-and-manual-codes-for-input-constrained-devices) only when regular sign-in is unavailable or particularly inconvenient, such as on a TV. Read [session renewal and account UI](references/sessions-and-ui.md) when implementing persistent sign-in, sync controls or account overview.

**Request `offline_access` by default for ordinary account sign-in.** The hosted X-Center ID authorization screen already lets users turn off **Stay signed in**. Do not add a second question, checkbox, or toggle in the app. Omit the scope for deliberately short sessions or when the app cannot securely handle renewal. If the issuer returns no refresh token, finish sign-in with a short session. See [session renewal](references/sessions-and-ui.md#keep-the-user-signed-in).

Start with the [platform-neutral developer guide](https://id.xcenter.it/docs#manual). For web apps or products with a backend, use the target stack's OpenID Connect library with a confidential website registration. For standalone native clients with callback ownership, use a public registration and the system browser with a verified HTTPS callback. For unsigned apps or clients that cannot receive callbacks, use the [backend browser handoff](references/integration.md#unsigned-apps-and-clients-without-an-app-callback). Use the SDK package that matches the existing stack. The protocol and hosted API work independently of UI frameworks.

**The recommended integration is a single `AccountOverview` at the top of Settings** when the SDK is compatible. It shows the X-Center ID sign-in banner or the signed-in profile in the same place. It already includes **Manage account & data**, **Open dashboard**, **Manage app**, and **Sign out**. Supply the host session adapters and optional settings. Use `RegisteredAppSignIn` only when the host needs a separate entry screen. Use the matching [package and setup guide](references/frameworks.md). The separate Expo entry component is documented in [Expo component specifications](references/sessions-and-ui.md#expo-component-specifications). A reusable sign-in view only supplies the entry point. Finish the host app's code exchange, validated account session, logout, secure persistence and error handling. When the target stack has no matching package, use its supported OIDC library and system browser with the same account card behavior. Check compatible versions before changing any framework dependencies.

The user's registration must be active before sign-in works. Each product needs its own registration, exact callback and application identity. Client IDs and icons are public metadata. A copied client ID cannot establish ownership. Keep confidential client credentials on the product's backend and use PKCE, state, nonce and validated issuer metadata. Public native clients depend on OS-verified HTTPS app links owned by that product. Declare Apple association records and Android asset links for the exact bundle/package and signing identity. If that ownership cannot be established, prepare the integration and report the missing callback requirement without enabling a substitute custom-scheme path.

Bind code exchange and login completion to a single-use transaction created before browser authorization. Validate the ID token's signature, issuer, audience, expiry and stored nonce. Identify users by issuer and subject. Existing accounts need explicit authenticated linking or a proven migration. Keep the provider's opaque access token separate from the product's own session and obtain live UserInfo or another supported validation before trusting it.

Verify cancellation, callback failure, process restart, wrong client, wrong callback, wrong PKCE verifier, replay, pending/revoked registration and unauthorized data access. Only report installation or device sign-in when actually executed. Document the installed files, portal identity, tested platforms and remaining activation steps in the target project. Registering a relying-party app does not authorize publishing it or changing another app.

Read the [capability reference](references/capabilities.md) to implement profile and email claims, required permissions, friend import, verified app storage, public data, and cross-app sharing. Use the dashboard for user-owned account management.

For actual reads and writes use the [data client and backend SDK guide](https://github.com/Xarber/xcenter-id-sdk/blob/main/docs/DATA_CLIENTS.md). Use a user token for delegated data, an anonymous client for public records, and a verified-app database key on the backend. Plain Node.js can handle the OAuth callback and app storage without React or Next.js.

If the portal shows that an administrator approved the registered callback URLs, have the registration owner confirm identity and use **Get client ID and secret** or **Get client ID** for a public native app. The approval covers those exact URLs. It does not replace the operating system’s app-link associations or enable the app badge and service database.

Use the SDK’s [configuration and sign-in guide](https://github.com/Xarber/xcenter-id-sdk/blob/main/docs/CONFIGURATION.md) for explicit settings, environment variables, and `xid.json`. Use a distinct public configuration file for a mobile or browser bundle. Put confidential OAuth and service database secrets into protected server configuration. Save only sessions whose callback and issuer identity the SDK validated.

## Administrative app scopes, larger files and peers

See the [SDK transport and account guide](https://github.com/Xarber/xcenter-id-sdk/blob/main/docs/ACCOUNT_AND_PEER_APIS.md) for calls in all supported SDK languages. Ask for `account_overview` or `account_manage` only if an administrator designated this registration as a trusted Administration app and the feature needs it. The user selects these under **Administrative App Permissions** and must explicitly confirm management access. Use scoped account APIs directly from the signed-in app. Account sign-in and new consent still use the supported issuer sign-in flow. Storage totals, public-profile visibility, and linked app access are the supported controls. Keep passwordless credentials and operator actions in X-Center ID.

Use resumable file transfers with `files_write` when files exceed the inline upload size. Account quota governs available storage. Verified apps can opt into WebRTC signaling and same-app discovery from Developer Apps. To appear in the directory, also open the peer with `discoverable: true`. Use `user.peers.list(session)` or the [browser adapter](https://github.com/Xarber/xcenter-id-sdk/blob/testing/docs/PEER_CONNECTIONS.md) for discovery. That adapter supports voice, video, screen streams and data channels. The host app handles invitations, media permissions and file acceptance.

## Binary files inside app containers

When an app stores backups or other binary data, prefer its own container files over creating a separate folder in the user’s ordinary Files. Request `app_data` and use `user.appFiles` or the native app-file methods. Pass `browseable: true` only for files the account holder should be able to open and download from the app’s branded folder. This visibility is independent of the developer’s record-browser toggle. For verified backend-owned files use `service.files` with a protected database key. The account and service quotas are separate. Use resumable chunks and document how to recover the transfer ID. See the [SDK container file guide](https://github.com/Xarber/xcenter-id-sdk/blob/70c3b31cafee0052831d1295375845bd97222064/docs/APP_CONTAINER_FILES.md) and [hosted reference](https://id.xcenter.it/docs/sdk/app-container-files).

If a project already uses stock PeerJS, keep that client and open a scoped PeerJS session through X-Center ID. Pass only the session key and socket proof to the Peer constructor, renew it with a current signed-in app token, and close it when leaving. See the [PeerJS setup](https://github.com/Xarber/xcenter-id-sdk/blob/main/docs/PEER_CONNECTIONS.md#unmodified-peerjs).

Set `editable: true` alongside `browseable: true` only for binary files the account holder should be able to rename, replace or delete. Existing Browseable files remain read-only unless the app grants Editable. Track the returned file ID and handle user edits and deletion as ordinary outcomes. Keep service files private.

For an app-managed file index, read the lowercase SHA-256 digest in `sha256` on each file list entry. Fetch one descriptor without downloading via `user.files.get(id)`, `user.files.getShared(shareId)`, `user.appFiles.get(id)`, or `service.files.get(id)`. Swift, Kotlin and Dart expose `getFile`, `getSharedFile`, and `getAppFile`. On direct HTTPS pass `?metadata=1` on the existing download route. Store both the file ID and digest. Renaming and moving preserve the digest. Identical bytes can exist under different IDs, and replacing bytes can change the digest under the same ID.

## App backups

Enable backups and a compatibility version in Developer Apps → Storage. With the user’s separate backup grant and `app_data` token, call JavaScript `user.appBackups.list()`, `.create()`, `.delete(id)` for app-created backups, or `.requestRestore(id)`. Swift, Kotlin and Dart use `listAppBackups`, `createAppBackup`, `deleteAppBackup` and `requestAppBackupRestore`. Open the shared user interface with `user.appBackups.managementURL()` or the issuer URL `/apps/{clientId}/backups`. The app can request restore but the user confirms it in the dashboard. Snapshots share unchanged file content and immutable record versions.
